# V1.0 synchronization baseline

Version **2.0.0** restores the video drift controller and shared transport barriers from the published `v1.0.0` tag, with the independent input-availability fixes listed below. The user requested reverting only drift-related work, while retaining newer client features. Stable 1.0 and its locked assets are unchanged.

## Restored behavior

- The host keeps v1.0's regression and rate bounds. Independent availability fixes select live exchanges from the latest three seconds, include measured RTT envelopes in midpoint-outlier selection, intersect compatible delay/oscillator intervals for confidence, bridge an unusable fit for at most 750 ms with increasing uncertainty, and calculate current source phase from the latest 250 ms. These do not add a new video drift controller or relax the 12 ms confidence limit.
- Three exchanges are still required for initial acquisition. Once acquired, one/two current exchanges can bound the phase of the established model without replacing its fitted rate. Confidence accounts for observation age and the prior model; repeated queries of old exchanges cannot renew the retained model, and unsupported estimates expire. Requiring three recent replies indefinitely had manufactured an outage despite valid sparse measurements.
- The phase estimate uses the center of the supported interval, minimizing its worst-case error. Retaining an estimate near one edge can unnecessarily exceed the unchanged confidence budget even when the interval itself supports a usable estimate. The original weighted rate fit remains.
- The host's scheduled start and coordinated recovery use v1.0 behavior. Progress verification additionally requires delivered audio anchors and an advancing TV master. Source sampling and monitoring discard unusable clock inputs rather than latching a single rejected measurement as a fatal error. No old anchor is re-stamped as fresh: local source observations still expire after 750 ms. A guard allowing new remote-library media remains in the start path.
- Affine modes use the same 12 ms phase-confidence budget at startup and during monitoring. They do not also impose baseline mode's 30 ms RTT heuristic: intersected valid intervals can support a narrow confidence bound despite a slower individual exchange. Baseline retains its original RTT checks, and affine source/delivery/TV expiry guards remain active.
- Frame-progress monitoring is independent of whether a clock correction was accepted. Old status packets are skipped rather than treated as proof of a frozen renderer; the existing two-second control-telemetry deadline still applies, and fresh reports of a stalled frame still fail after one second.
- The TV's slew/rate calculations use v1.0 math; post-1.0 projected-rate correction remains removed. Independent input validation matches the host's exact source/clock rate ratio and summed 10 + 12 ms uncertainty contract.
- Native video-renderer stop/re-enable events no longer freeze or reposition the independent HDMI-audio master. Repeated renderer starts preserve elapsed time. Coordinated host pause/seek epochs still reset the model, and leaving the Activity stops it. In audio-clock mode a video-only refill gets 200 ms to clear naturally before a full recovery; source expiry is checked first, audio-cache pauses recover immediately, and persistent video buffering still uses the original barrier. This is a renderer-availability correction, not a new drift calculation or retained-buffer transport protocol.
- Timing anchors use a dedicated transport; experimental control-channel fallback and retained-buffer recovery remain removed. Matching clients now negotiate [authenticated UDP timing](datagram-timing.md), with the original TCP path retained for compatibility. Local audio sampling runs independently of socket writes, with one latest-value slot instead of an outbound queue. A blocked send cannot stop source observation. A completed send only counts as current delivery if its original source observation is at most 250 ms old; delivery expires separately after two seconds. Clock mapping and saved lead are applied once, without changing source timestamps or compressed audio timing. Sender success does not establish TV receipt; receiver expiry remains guarded.

V1.0 already uses audio as master, synchronized monotonic clocks and bounded video-clock correction. Reverting the newer continuous-drift work does not remove those original synchronization mechanisms or disable error detection. Audio playback speed stays at 1x; no audio resampling or transcoding is introduced.

## Retained features and fixes

Saved phone/manual calibration remains in the same private profile. Subtitles, audio choices/defaults, browsing and UI features are retained. Client-state broadcasts remain on independent workers to service the new clients; these workers do not alter media time. The demonstrated milliseconds-to-microseconds overflow fix remains as a 64-bit adapter around the original TV reset method.

Baseline retains v1.0's 30 ms RTT guard; affine modes retain the 12 ms clock-confidence check and 500 ms stale-anchor rejection. Host source observations still expire after 750 ms. The TV may hold its last accepted model for at most two seconds, with uncertainty growing by 4 ms per second; it stops sooner if that exceeds the 22 ms combined input budget. Stale/rejected packets do not renew this deadline, and the original phase-jump guard remains. This addresses captured delivery gaps beyond 750 ms without changing audio timing or the video drift controller. These bounds describe the software model, not measured panel/receiver latency. Buffer recovery uses the original shared pause/prepare/start barrier; real starvation or prolonged/untrustworthy timing can still stop playback.

The diagnostic report retains a bounded, allowlisted `last_failure` observation before pausing resets the TV timeline. It includes relative numeric clock samples, without device addresses, clock origins, media paths or credentials. Current telemetry after a pause must not be mistaken for the pre-pause failure state.

## Verification

The controller, coordinator operations and renderer source were compared against the v1.0 tag. The comparison exposed an original clock-availability failure too; the explicitly listed input-freshness fixes remain. The prior four-hour drift simulations and experimental-delivery tests describe reverted work, not the active build. The candidate passed 151 host tests, 39 TV JVM tests and a 15-minute uninterrupted UDP movie run; see the current context for release packaging checks and remaining device coverage. User-reported excellent sync on the original setup is historical evidence, not proof of current hardware behavior or absolute physical accuracy.
